The verdict

Serve it FP8 with MTP 2, cap context at 16–32K

On a single GB10 this model is memory-bandwidth bound, and every result follows from that. The winning configuration:

  • FP8 over BF16, always. 28 GB of weights instead of 50 GB means fewer bytes moved per token. FP8 is 1.36–1.93× faster than BF16 at matched settings — the gap is widest on prompt-heavy work and narrows only when MTP lets BF16 borrow idle compute.
  • MTP is the single biggest lever — up to 1.7× (FP8) or 2.3× (BF16) for free. Best draft depth: 2 tokens for batched FP8, 3 for single-stream FP8, 4 for BF16. Beyond that, acceptance rate falls faster than acceptance length rises and throughput regresses.
  • Context is cheap on memory, expensive on latency. The KV cache pool never binds (65–71 GiB, still 7.7× concurrency at 262K). But decode throughput halves by 32K and time-to-first-token climbs to 117 s on a 110K-token prompt. Keep max-model-len at 16–32K unless you genuinely need more.
  • Keep the vision tower. A separate A/B shows loading it costs ~3 GB and a one-time ~2.5 min boot, with no text-throughput hit — and OCR reads a full invoice image in 6–7 s. Only add --language-model-only if you need the memory back.
Practical default --kv-cache-dtype fp8 --speculative-config '{"method":"mtp","num_speculative_tokens":2}' --max-model-len 32768 --gpu-memory-utilization 0.65 --limit-mm-per-prompt '{"image":1,"video":0}'  →  ~180 tok/s aggregate at 32 concurrent users, ~12 tok/s for a single user, OCR / vision available.
Speculative decoding

MTP draft-token sweep

The model ships a Multi-Token Prediction head. vLLM runs it as the draft model and verifies N speculative tokens per step. More draft tokens raise the acceptance length (tokens landed per verify) but lower the acceptance rate (fraction of drafts kept), and verification itself costs compute. Throughput peaks where those curves cross — N = 2 for batched FP8.

Why FP8 wins here The DGX Spark's LPDDR5x delivers a fraction of an H100's HBM bandwidth, so decode is gated on moving weights, not on math. Halving weight bytes with FP8 buys a near-linear speedup. BF16 also loses KV-cache room to its larger weights — ~29 GiB / 13× concurrency vs FP8’s 46–64 GiB / 40×.
Caveat The checkpoint carries no k_scale/v_scale, so the FP8 KV cache runs with a scaling factor of 1.0 — possible minor accuracy impact not measured here. This benchmark measures throughput and latency only, not output quality.

Vision

The vision tower is nearly free

This is a vision-language checkpoint. The benchmark ran text-only with --language-model-only. A separate A/B at the tuned 16K config — tower loaded vs skipped — shows keeping it costs almost nothing:

--language-model-onlyvision loadedΔ
16K · MTP 2 · FP8 KV · gpu-memory-utilization 0.65. Text tok/s differences are within run-to-run noise (~±5%).
OCR verified A 640×400 invoice image — all four text lines transcribed verbatim (#2026-0842, EUR 1,337.00, 2026-09-15, GB10-QWEN-BENCH) plus both shapes and colours, in 6–7.5 s. The image cost only ~250 context tokens. A full-page scan at higher resolution costs far more — cap it with --mm-processor-kwargs '{"max_pixels": ...}'.

Verdict: drop --language-model-only unless you need the ~3 GB back or the faster boot. It adds a one-time ~2.5 min to the first startup (vision-encoder compile, then cached) and no measurable text-throughput cost.

Environment

Setup & gotchas

  • Model. orcarouter/Qwen3.8-27B-Uncensored-FP8 — 27.8B, block-FP8 E4M3, hybrid attention (16 full + 48 Gated-DeltaNet linear layers), MTP head, 262K native context. The 43 sweep runs used --language-model-only; the vision A/B above measures the tower loaded.
  • Server. nvcr.io/nvidia/vllm:26.07-py3 (vLLM 0.24.0, CUDA 13.3, arm64). transformers 5.6.1 in the image is fine — vLLM uses its own qwen3_5 implementation.
  • DeepGEMM must be off. VLLM_USE_DEEP_GEMM=0 is mandatory: its UE8M0 FP8 path asserts Unknown recipe during kernel warmup on sm_121. vLLM falls back to CUTLASS block-scaled FP8.
  • MTP flag. --speculative-config '{"method":"mtp",...}'. The old --num-speculative-tokens is gone in 0.24.0.
  • Unified memory. --gpu-memory-utilization carves from the whole 128 GB pool. At 0.65, free shows ~87 GB used the moment the server is ready; context runs at 0.80–0.85 peaked at 105–114 GB. nvidia-smi reports N/A for all GPU memory on this part — the harness reads free -m.
  • Weight load. FP8 ~28 GiB in 110–180 s; BF16 ~50 GiB in 290–390 s. A mounted VLLM_CACHE_ROOT cuts recompilation on repeat starts.
  • One transient failure. FP8 / MTP 4 / 32-concurrent failed once (all requests, 0 output, no server error logged); re-ran clean at 177.7 tok/s. Not reproduced.
